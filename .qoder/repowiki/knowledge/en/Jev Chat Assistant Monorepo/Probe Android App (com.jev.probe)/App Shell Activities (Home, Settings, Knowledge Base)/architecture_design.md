Three sibling `AppCompatActivity` subclasses form the user-facing shell of the app with one-way outward dependencies:
- `MainActivity` is the launch/home screen: renders a readiness card (accessibility + overlay + key/hosted status), permission checklist rows, an optional hosted-mode card (`com.jev.probe.billing.EntitlementRepo`), and a master on/off toggle; navigates to `SettingsActivity` and `PlanActivity` via explicit Intents.
- `SettingsActivity` is the configuration hub organized into sections (接口 / 分析 / 外观 / 关于与隐私). Each API provider (judge/reply/vision) has its own pill selector, base URL + model + key inputs, and a smoke-test button that runs against a throwaway `Prefs` instance created by `draftPrefs()` so typed values never overwrite saved config. Network calls go through `JudgeClient`, `ReplyClient`, `VisionClient` on a single-thread `Executor`; results are posted back to the main thread via `Handler(Looper.getMainLooper())`. The knowledge-base entry point here launches `KnowledgeActivity`.
- `KnowledgeActivity` manages two tabs (notes, contacts) backed by `KbStore`, with inline edit dialogs and import flows; all data stays in the app-private `filesDir/kb` directory.

Dependency direction is one-way outward: these activities depend on `core.Prefs`, `core.kb.KbStore/KbSelfCheck`, `jev.*` clients, and `billing.EntitlementRepo`, but expose no interfaces themselves — they are leaf UI entry points consumed only by the Android manifest/launcher.
